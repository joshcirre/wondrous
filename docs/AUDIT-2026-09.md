# Wondrous audit: controls, animation, first match (September 2026)

Scope: a written audit against Josh's three goals. No product code was changed. Screenshots are attached to the draft PR as artifacts and referenced here by file name (for example `12_champion_selected_move_tiles_side_panel.png`).

## 1. Summary

Wondrous runs cleanly and a full ranked live match and a full practice game both played through to the end screen and replay. The rules engine is solid and fully server-authoritative. None of the three goals is met today, but the gaps are well contained. **Direct board control (goal 1)** is blocked by three things. Every attack or skill needs a side-panel mode button. A destination dropdown and a target list duplicate the board. And, most seriously, miniatures swallow clicks aimed at the tiles and enemies behind them: from the fixed camera angle, the tile straight ahead of a champion is covered by the neighbouring miniature. **Animation (goal 2)** is limited to a straight-line slide for moves and a one-second ring at a unit whose health or mana changed. Misses and blocks show nothing on the board, deaths vanish instantly, and the computer's whole turn lands in a single frame window. **Fast mastery (goal 3)** has no support yet. A new player's first practice game opens on a 12-card draft, then a formation step, then a board where the enemy is six rows away. Hit and block chances only appear as the text "95% hit · facing affects block", and recovery shows as a small "REST 2" stat. The server cannot currently tell the client which moves and targets are legal; the client re-implements movement and range rules in `Game.tsx`. The recommended order is: first, a server "legal options" payload with per-target hit, block and damage previews; second, click-to-move and click-to-attack on the board with the occlusion fixed; third, structured resolution events from the engine to drive an animation queue; last, a fixed-setup first-match scenario built on those pieces.

### 2.2 How a turn is played today

Code: `resources/js/pages/Game.tsx`.

1. Click a champion, on the board or in the roster. `select()` (L238–251) sets `mode = "move"`, and teal highlights come from a client-side BFS (`reachable()`, L32–64).
2. Click a highlighted tile to move (`tile()`, L252–273), or pick a coordinate such as "H1" in the **Destination** dropdown (L1034–1079). After the move, highlights disappear and the mode stays "Move", with the Move button disabled (`14_after_move_no_highlights_mode_still_move.png`).
3. To attack, click the **Attack** button (L880–896), or the **skill** button (L898–926). Only then are targets highlighted (L182–199, L217–222), and a **target list** of buttons appears in the side panel (L933–989).
4. Click the enemy on the board or in the target list.
5. Change facing with a **Facing** `<select>` (L990–1031).
6. Click **End turn**.

### 3.2 Against goal 2

Today, animation is a reaction to snapshot diffs, not a depiction of what happened. The renderer doesn't know who attacked whom, whether a roll missed or was blocked, which path a move took, or that a skill was cast, because the client receives none of that as data. It only exists as English log lines. This is the root cause, and section 5.4 describes the seam that fixes it.

## 5. Engineering checks

### 5.1 Where move and attack are validated, and can the server hand the client the legal options?

**Validation today.**

- HTTP entry: `POST /games/{code}/actions` → `GameController::action()` (`app/Http/Controllers/GameController.php` L53–60). It allowlists `type` and forwards `unit_id`, `target_id`, `x`, `y`, `facing`.
- Serialization: `MatchService::act()` → `applyLocked()` (`app/Services/MatchService.php` L51–102). It takes a cache lock and a row lock, checks participation and the version precondition, then calls the engine.
- Rules: `App\Game\GameEngine::apply()` (`app/Game/GameEngine.php` L21–166), all in pure PHP arrays:
  - phase and turn (L114–115, `turn()` L321);
  - ownership and alive (`unit()` L344–356);
  - recovery, stun and one active champion (L125–127);
  - move: already moved, root, integer tile 0–7 (`tile()` L358–365), path (`reachable()` BFS L388–421: orthogonal, living units block, within `move`);
  - attack and skill: already acted, target team, Manhattan `distance()` ≤ range (L142–149), cooldown and mana (L150–154);
  - resolution in `damage()` (L213–251) and `cast()` (L168–211).
- Persistence: `MatchService::record()` (L200–212) fires the Verbs event `App\Events\MatchAdvanced` with the **fully resolved** board (`result`). `MatchAdvanced::apply()` only restores that board into `App\States\MatchState`. **Verbs events do not validate.** They are records, so replays never re-roll.

**Can the server list legal targets today? No.** There is no endpoint or field for it. `reachable()` answers yes or no for one tile and is private, as are `distance()` and `blockFactor()`. The client fills the gap with its own copy (V9). The engine can already act as an oracle, though: `ComputerOpponent::choose()` (`app/Game/ComputerOpponent.php` L53–103) enumerates candidate moves and attacks by calling `apply()` on an isolated engine with a fixed random callback (L13–16) and catching `GameRuleException`.

**Smallest server change.** Add a public `GameEngine::options(array $s, int $viewerId): array` and return its result as a sibling of `state` in `Game::visibleTo()`, so it isn't persisted into events or `game_records`. Only compute it for the turn player in `battle`. Build it by dry-running every candidate through `apply()` on a no-randomness engine, exactly as the computer does. That guarantees zero drift; the cost is at most 6 units × (64 tiles + 12 targets × 2) dry runs on small arrays per read. Suggested shape:

```json
"options": {
  "version": 57,
  "units": {
    "1-ranger": {
      "can_activate": true,
      "reason": null,
      "moves": [{ "x": 3, "y": 4, "path": [[3, 6], [3, 5], [3, 4]] }],
      "attack": [
        { "target_id": "-1-warden", "hit_chance": 90, "block_side": "front",
          "block_chance": 40, "damage_on_hit": 17, "land_chance": 54 }
      ],
      "skill": {
        "usable": true, "reason": null, "cost": 18,
        "targets": [{ "target_id": "-1-warden", "effect": "damage", "amount": 34, "always_hits": true }]
      },
      "facing": ["north", "east", "south", "west"]
    },
    "1-knight": { "can_activate": false, "reason": "This character is recovering." }
  }
}
```

- `reason` reuses the engine's own `GameRuleException` messages, so disabled states explain themselves with server text.
- `path` needs a BFS that returns the path (a small extension of `reachable()`); animation needs it too (5.4).
- After a move, the next response carries fresh options from the new tile, so move-then-attack needs no client logic. Optionally, add `moves[].threatens: [target_id]` to show which enemies a destination brings into range.
- Also return `options` in the `POST /actions` response, and delete `reachable()` and the `targets` memo from `Game.tsx` once it lands.

### 5.2 Can each target include hit and block chance by facing from the server's own math?

**Yes. All the math is in `GameEngine::damage()` today:**

- Hit: roll 1–100 ≤ attacker `accuracy` from `CharacterCatalog` (L219–226). Values: 95 for most champions, Ranger 90, Ember Witch 92.
- Block: `floor(defender.block × blockFactor(attacker, defender))` (L227). `blockFactor()` (L377–386) returns 1.0 from the front, 0.5 from the side and 0.0 from the rear, using `direction()` (L372–375: dominant axis; exact ties use the vertical axis). This matches RULES.md. Block is rolled only after a hit.
- Damage on a landed hit: `min(hp, max(1, attack − armor))`, where armor = catalog armor + 12 with ward + 4 if a living allied Herald is within two tiles (L236–243).
- Skills skip both rolls. Their amounts live in the `match` inside `cast()` (L191–193), for example Backstab: 52 if `blockFactor === 0.0`, else 32. Heals are 38 for Cleric and 25 for Druid.

**Refactor needed** so the preview and the roll can never diverge: extract private `blockChance($s, $i, $j)`, `armorFor($s, $j)` and `skillAmount($s, $i, $j)`, and call them from both `damage()`/`cast()` and `options()`. Report `hit_chance`, `block_chance`, `block_side` and `damage_on_hit`. Report `land_chance = hit × (1 − block)` as well, because "95% hit, 40% block" is easy to misread. Skill amounts are also duplicated as prose in `CharacterCatalog` descriptions, which is a second drift risk worth folding in at the same time.

### 5.3 Can Play against computer start from a fixed setup with a guaranteed turn-1 hit, without rigging dice?

**A fixed setup: yes, with a contained change.**

- **Scenario data:** a new `app/Game/Scenarios/FirstMatch.php` (pure data) listing both squads with `x`, `y` and `facing`.
- **Start state:** in `MatchService::create()` (practice branch, L27–44), accept an optional `scenario` from `POST /games`, validated in `GameController::create()`. Build the state directly in `phase=battle`: set `turn_player_id` to the host, `turn_number=1`, `ready=[host, -1]`, fill `draft_picks` so the replay's draft overlay still works, and add the units from the scenario. Record it through the normal `record()` path so events and replays work unchanged. Put `scenario` and `lesson_step` in state as additive fields.
- **Opponent behaviour:** `ComputerOpponent::choose()` needs a scenario branch. For the first few turns it should play scripted commands, still through the real engine: for example, turn its knight's back for the facing lesson and avoid killing the resting attacker. After that it falls back to the search. Without this, the current search attacks immediately and can break lessons 2–3.

**A guaranteed hit by positioning alone: no, not for a basic attack.** Positioning controls block (a rear attack sets block to 0), but not accuracy. No champion has accuracy above 95 (`CharacterCatalog`), so the best honest basic attack lands 95% of the time; a Velvet Rogue from behind has 95% to hit and 0% to block. Options, in order of preference:

1. Accept 95%. Use a rear attack by a 95-accuracy champion, and write the lesson so a miss is handled ("Misses happen, 5% here, and your action is still spent"). That also sets up turn 3.
2. Make the turn-1 action a skill, which always hits. This reorders the brief, which introduces skills on turn 4.
3. A seeded RNG chosen so the first roll hits is rigging and should not be used. The engine's injectable `random` callback (`GameEngine::__construct`) is for tests.

Changing the rules (for example "rear attacks always hit") would apply to every game and is out of scope for a tutorial.

### 5.4 Current animation stack, what drives it, and the seam for richer animation

- **Stack:** React Three Fiber `Canvas` with an orthographic camera, OrbitControls (bounded, no pan) and procedural meshes. Per-frame motion comes from `useFrame`: `Pawn` position and facing lerps, `CombatEffect`, `Miniature` bob, braziers and leaves. There are no animation clips, skeletons, tween library or particle system beyond `Points`.
- **Driver:** entirely client-side diffing of successive server snapshots (`state.units`). The server sends no action or outcome data to the renderer. The replay page (`Replay.tsx`) steps through stored snapshots every 1.8 s ÷ speed, with the same lerps. `game_records` stores command payloads, but replays deliberately omit them (CONTRACT.md).
- **Seam (recommended):**
  1. **Engine emits structured events.** At the start of each `apply()`, reset `$s['events'] = []`, then append typed entries next to the existing `log()` calls, for example:
     - `move {unit_id, from, to, path}`
     - `attack {unit_id, target_id, side, roll: {accuracy, hit_roll, block_chance, block_roll}, outcome: hit | miss | block, damage}`
     - `skill {unit_id, skill, target_ids, amounts, statuses}`
     - `status_tick`, `death`, `turn_start`

     Because `MatchAdvanced` and `game_records` persist the full resolved state, events are recorded and replayable for free, with no re-rolling. It is an additive field, as ARCHITECTURE.md requires. The same data can later produce plain-language, owner-qualified log lines (fixing the mirror-name ambiguity) and the end-screen "decisive moment".
  2. **Deliver every step, not just the latest snapshot.** Add `GET /games/{code}/events?since={version}`, reading `game_records` (participant-only, same filtering as `visibleTo`). The client can then play a computer turn or a coalesced opponent move + attack as separate beats.
  3. **Client animation director** in `Battlefield`: a queue keyed by `(version, index)` that plays walk-along-path, attack or cast clips, projectiles, impact, floating "Hit −21 / Blocked / Miss", and death. It holds the displayed snapshot until the queue drains, then **snaps to the authoritative `state.units`**. Input is disabled or queued while it plays. On a version gap, reconnect or `prefers-reduced-motion`, it skips straight to the snapshot. Animation can lag the server, but it can never disagree with it.
